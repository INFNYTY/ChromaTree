# 实现的契约

[English](../en-US/contract.md) | **简体中文**

> [spec.md](spec.md) 讲的是语言，这份文件讲的是一个实现。任何语言的 ctree 实现，
> 只要满足下面写的东西，就算实现了规范 0.3。
>
> 契约说的是“要能回答什么”，不是“用什么类型回答”，所以实际签名放在各个实现自己的 API
> 契约里，清单见 [README.md](../README.md)。
>
> 判据是 [conformance/](../../conformance/) 里那批用例，跑得过才算数。

---

## 1. 四条边界

1. 实现不做任何 IO：不读文件、不读环境变量、不看当前目录。因为求值与检查都是纯函数，
   真实树以段序列的形式由调用方传进来。能不能在编译期强制、用什么手段强制，由各实现自己
   决定，理由见 [design.md](design.md)。
2. 实现不带任何业务词汇，不知道哪个颜色是特殊的。凡是要用到“哪些颜色有意义”的地方，
   颜色表都由调用方传进来。
3. 实现不说任何自然语言：诊断只给类型加位置，不出文案，文案由调用方按自己的语言与措辞生成。
   实现另外提供一个稳定的短码（形如 `CT0107`），专供日志与问题追踪，它是一个键，不是一句话。
4. 名字是不透明的，实现不认识任何分隔符。路径进来是段序列，出去也是段序列。

## 2. 名字与路径

规范说节点名是“声明行里那个空格之后的整行，trim 后原样保留”（spec §4.1），
所以名字可以是任意字符串，包括含 `/`、含空格、含五大符号的字符串。

实现因此不会自己切分任何东西，调用方若要按 `/` 分层，就得自己先切好再传进来。

段序列 `[]`（空）表示匿名根（spec §2.7）。

## 3. 必须暴露的操作面

| 操作 | 语义 |
|---|---|
| 解析 | 一段文本 → 一份文档，或全部诊断。只要有错误就不产出文档（不做错误恢复式的部分 AST）。 |
| 检查 | 文档 → 诊断。不需要真实树。 |
| 带词表的检查 | 同上，外加“颜色必须在给定的词表里”。 |
| 单条查询 | 文档 + 段序列 → 颜色，或“不表态”。不需要真实树。 |
| 批量求值 | 文档 + 一批路径 → 一个可以反复查询的结果。 |

单条查询是核心：开放世界（spec §2.6）下，一条路径的颜色由文档结构与规则决定，
与真实树里有没有它无关，其余操作都是它的派生。

批量求值要能回答：

| 查询 | 语义 |
|---|---|
| `color_of(p)` | 集合里任意路径的颜色 |
| `paths_with(c)` | 集合里颜色为 `c` 的路径 |
| `roots_of(c)` | 颜色为 `c`、且父路径颜色不是 `c` 的路径，也就是“哪几棵子树整体是 `c`” |
| `exceptions_within(root)` | `root` 子树内颜色与 `root` 不同的路径，也就是块根被谁打穿 |
| `counts()` | 集合里每种颜色的路径条数 |
| `unmatched()` | 文档声明了、但集合里没有的节点 |
| `explain(p)` | 影响这条路径的全部规则，按行号升序 |

- `roots_of` 的父路径颜色是结构性地问出来的，不要求父路径在集合里，
  否则只给叶子路径的调用方会得到错误结果。
- `unmatched` 的判据是“集合里没有谁等于它、或落在它之下”，
  否则只给叶子的调用方会被误报一堆中间目录。
- `explain` 的最后一条才是生效的那条，它给出的源码位置是“这条判定来自哪一行”的唯一来源。

每条判定要带四样东西：路径、颜色、源码位置、怎么来的。最后一样是 `@` 直接染的、`>` 直接染的，
还是从祖先继承的；它让调用方区分“作者点名的”与“继承来的”，而只有前者才算一次操作。

## 4. 求值的精确定义

一条规则有一个起点：`@ c` 在节点 A 的作用域内时起点是 A；`> c` 的目标是 T 时起点是 T
（且 T 是隔离路径时整条规则被忽略，spec §2.3）。

从起点 O 出发，颜色 `c` 到达节点 V，当且仅当：

- `V` 就是 `O`，或
- 从 `O` 到 `V` 的路径上，每个中间节点都是递归路径，且 `O` 不是中止路径，
  且 `V` 不是隔离路径。

路径 `P` 的颜色，是所有到达 `P` 的规则中行号最大的那条的颜色（spec §2.5）；
没有规则到达则不表态。

## 5. 诊断

### 5.1 清单

结构类

| kind | severity | 触发 |
|---|---|---|
| `TabIndent` | Error | 缩进里出现 Tab |
| `IndentBase` | Error | 基准缩进不是 2 / 4 / 8 |
| `IndentMixed` | Error | 某行的缩进不是基准的整数倍 |
| `IndentJump` | Error | 子节点比父节点深出不止一级 |
| `UnexpectedLine` | Error | 一行不属于空行 / 注释行 / 声明行 |
| `MissingSeparator` | Error | 符号之后没有空格 |
| `EmptyName` | Error | 声明行里符号之后没有名字 |
| `StopHasChildren` | Error | 中止路径带了子节点声明或 `>` 规则 |
| `EmptyTargets` | Error | `>` 规则一个目标也没有 |
| `RuleOutsideScope` | Error | 染色规则落在任何节点作用域之外 |
| `EmptyDocument` | Warning | 文档里没有任何节点声明 |

语义类（纯文档判据，不需要真实树）

| kind | severity | 触发 |
|---|---|---|
| `DuplicatePath` | Warning | 同一路径被声明多次。不是错误：两条声明里的规则都参与求值，路径类型由后一条定（spec §2.8） |
| `ExplicitTargetIsolated` | Warning | `>` 的目标解析出来是隔离路径，该目标被忽略，规则是冗余的 |
| `DeadRule` | Warning | 一条规则被行号更大的规则完整覆盖（部分覆盖不算） |
| `ConflictingRule` | Warning | 同一作用域内两条 `@` 给出不同颜色 |
| `RedundantRule` | Warning | `@ c` 而祖先已传播 `c` 下来且中间无隔离路径 |
| `UnknownColor` | Error | 颜色不在调用方给的词表里 |

### 5.2 短码

`conformance/codes.json` 是短码的权威表，也是唯一一份。
kind 的完整清单在本文件，码值在那份 JSON，两边分开是因为码值是机器要读的、清单是要人读的。

短码一经发布不再改变含义，新增诊断用新码，不复用旧码。每个实现都应当写一条测试，
比对自己的枚举或常量表与那份 JSON 一致。

### 5.3 死规则的实现要求

它的“覆盖”判定必须与求值共用同一份传播计算。若两处各写一套，迟早分叉，那时检查器说“这条不会生效”
而求值器照用不误。“同一份语义只判一次”在实现内部同样成立。

## 6. 什么不在契约里

- 序列化形态不在契约里，各实现自己定。目前也不需要跨语言交换文档，因为消费者之间交换的是摊平后的操作序列，
  不是染色树。
- 写回源码的排版也不在契约里：只承诺幂等（写出去、解析、再写出来逐字相同），不承诺缩进宽度，
  也不承诺保留注释。
- 便利 API 比如统计、声明列表之类，有则更好，没有不违规。
- 各语言惯用的类型也不在契约里。见本文件开头那句。

## 7. 一致性测试

语料在 [`conformance/`](../../conformance/)，是一批 JSON。
每个实现写一个小 harness，读它、跑它、报告。

```jsonc
// 一个用例可以同时带求值、诊断与查询断言；三类文件只是按主要关切分组。
{
  "name": "tutorial/first-example",       // 唯一，失败时用它指路
  "note": "教程 §1",                       // 可选，给人看
  "source": "- root\n    @ default\n",     // 或 "source_file"，相对仓库根
  "vocabulary": ["allow", "deny"],         // 可选：给了就跑“带词表的检查”
  "eval":  [{ "path": ["root","fileA"], "color": "special" },
            { "path": ["root","missing"], "color": null }],
  "errors":   [{ "code": "CT0105", "line": 2, "related": [3] }],
  "warnings": [],
  "paths": [["mods"], ["mods","cache"]],   // 批量求值用的路径集合
  "roots_of": { "delete": [["mods"]] },
  "paths_with": { "special": [["root","fileA"]] },
  "counts": { "delete": 4 },
  "exceptions_within": [{ "root": ["mods"], "paths": [["mods","saves"]] }],
  "unmatched": [["root","nowhere"]],
  "explain": [{ "path": ["mods","saves"],
                "chain": [{ "color": "delete", "line": 2, "via": "inherited" }] }]
}
```

- 路径是段数组，不是 `"a/b"` 字符串，因为名字不透明、可以含 `/`，字符串形式有歧义。
- 诊断是精确集合语义，多报一条也是不通过：规范列了检查清单，多出来的是不合规，
  而不是“更严格”。`errors` / `warnings` 缺省表示“本用例不断言诊断”，
  写成 `[]` 才表示“断言一条都没有”，两者不同。
- 不规定报告顺序，集合相同即可。
- `related` 只在写了的时候才断言，因为多数诊断没有相关的第二处。
- 语料不分版本目录：版本写在每个文件的 `spec` 字段里，旧版本靠 git tag 留档。

`source` 与 `source_file` 二选一，后者相对仓库根，
这样 `examples/` 里的示例文件不必在语料里再抄一份。
