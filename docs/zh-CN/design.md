# 设计取舍

[English](../en-US/design.md) | **简体中文**

> 这份文档记录为什么是这样，尤其是那些被考虑过又否决掉的方案。
> 规则本身见 [spec.md](spec.md)，实现的契约见 [contract.md](contract.md)。

---

## 1. 库不碰 IO

求值与检查是纯函数，真实树以段序列的形式由调用方传进来，库不读文件，也不读环境变量。

开放世界（spec §2.6）意味着“文档描述了哪些颜色”与“真实树里有什么”本来就是两件事，
把它们合进一个 API 等于让库去猜调用方想用哪棵树。纯函数还可以无条件地做属性测试，
不需要临时目录，不需要环境变量，也不需要清理，这是本库相对同仓其他模块最大的测试优势。
另外，“检查”与“求值”对同一份文档必须给出同样的结论，而一份文档可以对着十棵不同的树
求值，这只有在求值不持有树的时候才自然。

这一条可以编译期强制，只是手段因实现而异，各实现自己的 API 契约里记录它选了什么手段。
“零 IO”本身是共享的部分，写在 [contract.md](contract.md) 里。

## 2. 名字不透明

节点名与颜色名都是“声明行里那个空格之后、直到行尾的整行，trim 后原样保留”。
库不认识任何分隔符，不做切分，也不做拼接。

理由是语言有五个符号，它们构成全部的语法。引入 `/` 就是引入第六个符号，哪怕它只在
一处出现，语义面也变了：从此“名字”有两个层次，段与路径，`a/b` 与 `a` + `b` 的关系
需要定义，转义需要定义，绝对路径需要定义。而这些都与“在树上染色”这件事无关，
只是某一个使用者恰好用 `/` 分层。

代价是调用方要自己切分与拼回，不过写文件树的那类调用方会这么做一次，然后忘掉它。

直接后果是文档里写不出“一条规则点名一个孙辈”，因为 `- textures/foo.png` 只能匹配
一个真实的段，而按 `/` 切分后的真实路径里没有哪一段长这样。要写嵌套：

```ctree
- textures
    > delete
        | foo.png
```

这是有意的：深度由缩进表达，不由名字里的分隔符表达。

## 3. 词汇表不在库里

库不知道任何颜色是特殊的。`check_vocabulary` 的词表由调用方传进来，
`Stats::colors` 只是把文档里出现过的颜色列出来给调用方用。

理由是 `protect`、`delete` 这些词是使用者的业务词汇，不是语言的词汇，规范里也明说
“颜色没有任何保留字”。库一旦内置一组，就同时内置了它们的语义，再想换个词表就得改库。

顺带的好处是，同一个 ctree 可以用来描述权限、UI 主题、资源树，
因为它一个业务词都不认识。

---

## 4. 诊断不出文案

`Diagnostic` 只有 `kind`、`span`、`severity`、`related`，
文案由调用方按自己的语言生成。库另给一个稳定的 `code()` 供日志用。

库一旦写死文案，那条字符串就以打包时的语言被永久烙进产物里，而使用者的界面语言与
打包者的语言没有任何关系。多语言本来就是调用方的事，库提供 `kind` 就是为了让调用方
能挂着它做一张 `kind → 文案` 的表，且编译器能检查这张表有没有漏项。

代价是调用方必须自己写那张表，这是可接受的，因为他们本来就要做本地化。

实现可以把“不产出自然语言”从纪律变成断言，办法是写一条测试，要求它为一个诊断渲染出来
的东西只有纯 ASCII，不带自己的文案。

---

## 5. 诊断带 `code()`

在“不出文案”的前提下，库仍然给每个 `DiagnosticKind` 一个稳定短码，比如 `CT0107`。

理由是日志与问题追踪需要一个不随文案变化的标识。使用者用中文说“第 12 行那个错误”，
开发者拿到的是另一句话，而 `CT0107` 两边都一样。这不违反上一条，因为它不是句子，
是一个键。

约定是一经发布不再改含义，新增诊断用新码，不复用旧码。

## 6. 被否决的方案

### 6.1 `sep` 参数（否决）

考虑过的方案是 `evaluate(doc, tree, sep)`，库用 `sep` 把祖先名字拼起来再切开，
以便支持 `- textures/foo.png` 这种“一条规则点名孙辈”的写法。

否决它的理由是，这等于把 `/` 换个马甲变成了第六个符号。库一旦理解“这个名字里有
分隔符”，它就有了路径语义：空段怎么办，连续两个分隔符怎么办，前导或尾随分隔符
怎么办，这些都得定义，而它们全都与染色无关。

最终取代它的是名字不透明（§2）、深度交给缩进、切分交给调用方。

### 6.2 宽松词法：忽略不带起始符的行（否决）

考虑过的方案是，由于缩进与换行的存在，解析器可以忽略任何不以五大符号开头的行。
文档自由度最大，作者可以在里面随便写散文。

否决它的理由是，它的失败模式是静默的。漏写一个 `-`（`- mods` 写成 `mods`）不会报错，
那一行连同它下面缩进的子节点会被挂到前面最近的那个节点上，作者以为结构没变，
实际整棵子树挪了位置，而且没有任何提示。

一个声明式语言的全部价值就在于把作用域说得毫无疑义，所以宁可报错，不要猜。
因此现在，不属于空行、注释行、声明行三类的行，一律报 `UnexpectedLine`。

### 6.3 行内注释（否决）

考虑过的方案是 `#` 与 `//` 在行内任意位置起始注释。

否决它的理由是，这与“名字取到行尾、不转义”直接冲突：`- a#b` 里的 `#` 到底是名字的
一部分还是注释的开始？两个方案都要额外规则，要求前置空格，或者在名字里禁用 `#`，
而注释独占一行不花任何代价，它不与任何东西冲突，还让“一行是什么”这件事继续是三选一。

### 6.4 文档是森林（否决）

考虑过的方案是顶层允许并列多个根。

否决它的理由是，寻址会变得含糊：一条路径从哪个根算起，给顶层节点加名字，
还是要求使用者自己指定根？而“文档是一个匿名根”让所有这些问题消失，根就是空路径，
顶层节点是它的孩子，顶格的 `@` 正好是“整篇都染”这个有用的意思。

### 6.5 重复声明是警告，不是错误

同一个路径声明两次不拦解析，只报一条警告。两次声明里的规则都参与求值，按行号排先后，
路径类型由最后一条声明决定。

理由是，语言本来就把“后规则覆盖先规则”当作基本法则，那没有理由在“同一个路径被
写了两遍”时突然变成硬错误。而且第二次声明往往是有意的，先铺一层，后面再改一处，
与 CSS 里同一个选择器写两个规则块的写法一样。判成错误会逼作者把它们揉成一段，
反而更难读。

代价是路径类型也跟着“后定义的生效”了，于是 §2.5 那句“节点声明不参与顺序”不再成立。
这是这条取舍真正的代价，因为结构本该与顺序无关，现在有一处例外。

它仍然值得：不留这个例外，就得在两次声明类型不同时挑一个赢家，而任何挑法都需要一个
顺序依据；既然顺序依据本来就在，不如直说用最后一条。

曾经的样子是，起初判成错误，理由是“同一条路径被声明两次”等价于两个节点争同一个
地址。那个理由站得住，但它带来了更糟的东西：求值器只认第一个同名节点，第二条声明的
规则静默消失。本设计一贯拒绝的失败模式就是它，所以宁可放宽成警告，
也不留一条静默错位的路。

### 6.6 为什么是求值，而不是时间顺序

一条规则用到的路径类型，取整份文档定下来的那一个，也就是同名声明取最后一条，
不是“执行到那一步时文档已经写了什么”。§2.9 那处说明就是这条。

ctree 是声明式的，时间式会让一条规则的效果取决于它在文件里的位置，读文档的人得在
脑子里维护“此刻这条路径是什么”，而 §2.9 那个心智模型（命令式遍历）本来是给人读
文档用的，不该反过来决定求值。§2.5 那条总则也保持一句话说得完：一条路径的颜色，
取决于能到达它的规则里行号最大的那条，而“能到达”是结构上的判定，与执行到哪一步
无关。CSS 也是非时间的，同一个选择器写两个规则块，后一个赢，与元素出现在哪里无关，
§2.8 已经向 CSS 看齐，这条也该跟着。

代价是求值器里的传播判定是一个静态谓词，路径类型在整份文档上解析一次。这条代价
还买了一件事，实现与文档同构，§2.9 描述的“从起点向下走”可以真的照那样实现。

分歧只在极窄处出现，同一个路径被声明两次、类型不同、且中间夹着规则。语料里
`declaration/*` 两条用例把它钉住了。

## 7. 与姊妹项目的关系

本库不依赖、也不认识任何特定的使用者。使用者特有的关切，例如“我不接受没有颜色的
节点”，应当由使用者在自己的那侧写校验器表达，而不是让语言内置一个只对他们成立的
规则。
